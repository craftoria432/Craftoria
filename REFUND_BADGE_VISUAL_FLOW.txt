REAL-TIME UPDATE MECHANISM
════════════════════════════════════════════════════════════════════════════════

Mobile App (Buyer)              Firestore DB                Web Dashboard (Seller)
─────────────────              ────────────                 ──────────────────────

Payment History                 seller_payments
  Open screen            ──→      Collection
  |                               (status = "completed")
  | Real-time             
  | listener          
  | attached          
  |
  └─→ Listening...


SELLER UPDATES REFUND STATUS ON WEB DASHBOARD
                                    ↓
                          Firestore document updated
                          (status = "refund_pending")
                                    ↓
        BuyerPaymentViewModel listener fires
        .addSnapshotListener() detects change
                                    ↓
        fetchAndPublish(buyerId) called
        Fetch latest payments from Firestore
                                    ↓
        publishPayments(payments) updates UI
                                    ↓
        Compose re-renders badge with new status
                                    ↓
    BUYER SEES INSTANT UPDATE
    Badge: "Completed" → "Refund Pending"
    No manual refresh needed! ✅

IMPORTANT: NO MANUAL REFRESH NEEDED! ✅
════════════════════════════════════════════════════════════════════════════════

The BuyerPaymentViewModel attaches Firestore listeners that:

1. Monitor "seller_payments" collection for changes
2. Automatically fetch fresh data when changes detected
3. Update UI in real-time via Compose
4. Support both cache-first (instant on revisit) and fresh (cold start)

Buyer doesn't need to:
❌ Manually refresh the screen
❌ Navigate away and come back
❌ Wait for polls
❌ See loading spinners on updates

Everything happens automatically! ✅


STATS CALCULATION
════════════════════════════════════════════════════════════════════════════════

Total Spent = Sum of (Completed + Pending + Processing payments)
            ✅ EXCLUDES refunded payments (buyer got money back)
            ✅ EXCLUDES rejected refunds (already paid)

Example:
├─ Completed:   PKR 10,000 ✓ (counts)
├─ Pending:     PKR 5,000  ✓ (counts)
├─ Processing:  PKR 3,000  ✓ (counts)
├─ Refunded:    PKR 2,000  ✗ (EXCLUDED - money returned)
├─ Failed:      PKR 1,000  ✗ (EXCLUDED - payment failed)
└─ Total Spent: PKR 18,000


FILTERING WORKFLOW
════════════════════════════════════════════════════════════════════════════════

1. User opens Payment History
   ↓
2. All payments shown with their current badges
   ├─ Completed (green badge)
   ├─ Refund Pending (orange badge)
   ├─ Refunded (purple badge)
   └─ etc.
   ↓
3. User clicks filter tab (e.g., "Refund Pending")
   ↓
4. List filters to show ONLY payments with status = "refund_pending"
   ↓
5. All other statuses hidden until filter cleared
   ↓
6. Real-time listener still active - list updates if any payment status changes
